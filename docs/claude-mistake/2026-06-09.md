## 2026-06-09 18:28 (KST) — 새 파라미터(require_fresh)를 호출부·본문에만 넣고 시그니처 누락 → 전체 픽 크래시, 단위검증이 못 잡음

### 무엇을 했는가
ptp pick&place 안전 보강 [3] 단계에서 `experiments/ptp_pick_resident.py` 에 sense-plan-act 재검출 핸드셰이크를 추가했다. `_do_one` **본문**(line 297 `if require_fresh and ...`)과 **호출부**(line 222 `self._do_one(self._color(), require_fresh=True)`)에 `require_fresh` 를 넣었으나, **정의 `def _do_one(self, color):` 시그니처에 파라미터를 추가하지 않았다.** 그러고도 "[3] SIL 검증 6/6 통과"라고 보고했다.

### 무엇이 잘못이었나
- auto 픽 → `TypeError: _do_one() got an unexpected keyword argument 'require_fresh'`, 수동 픽 → `NameError: name 'require_fresh' is not defined`. **수동·자동 픽이 전부 런타임 즉사**(하드 회귀).
- 더 나쁜 점: TypeError 가 함수 본문 진입 전에 터져 같은 세션에서 추가한 다른 안전장치([0b] SH 경로락, [2] 검출 게이팅, [3] staleness)가 **auto 경로에서 전부 무력화**됐다(SH 락을 안 잡으니 검출 게이팅도 안 걸림). 게다가 watchdog 이 `exception` 을 고장으로 집계해 5틱 만에 auto 자가정지.
- 내가 돌린 [3] SIL 테스트는 `_watch_auto` 와 freshness **비교 로직만 격리**(언바운드 메서드를 가짜 객체에)해서 검증했고 **실제 `_do_one` 을 한 번도 호출하지 않았다.** `py_compile` 은 문법만 봐서 `require_fresh` 가 미정의 이름이어도 통과. 결국 내 단위검증이 통과했다고 **잘못 보고**했고, 결함은 별도로 띄운 10인 적대적 검사가 잡았다(critical 11건 = 전부 이 한 버그).

### 사용자 지적
직접 코드 지적은 아니지만, 검사 결과를 보고하자 사용자가 "정말 간단한 구조인데 이렇게 문제가 심각한 이유는?" 이라 물어 실제 확정 결함을 들여다보게 됐고, critical 11건이 모두 이 시그니처 누락임을 확인 → 즉시 `def _do_one(self, color, require_fresh=False):` 로 수정.

### 사유 / 가설
- 파라미터를 추가할 때 **호출부+본문은 고치고 def 시그니처를 빠뜨림**(부분 편집의 전형적 누락).
- 검증을 **실제 호출 경로가 아니라 로직 격리**로만 설계 → 시그니처 vs 호출부 불일치는 호출 시점에만 드러나는데 그 시점을 안 거침. `py_compile`/import 통과를 "검증 통과"로 과신.

### 재발 방지
- **파라미터 추가 시 3종 동시 점검**: ① `def` 시그니처 ② 모든 호출부(`grep -n "_do_one("`) ③ 본문 사용처 — 셋을 한 번에 대조.
- **검증은 실제 호출 경로를 한 번이라도 실행**해야 한다(로직 격리만으로 "통과" 보고 금지). 최소 스모크: 해당 함수를 기본 인자 1회 + 새 인자 1회 직접 호출. `py_compile`/import 성공은 문법·임포트만 보증하며 런타임 NameError/TypeError 를 못 잡음.
- 반영 자산: 코드 수정 [experiments/ptp_pick_resident.py](../../experiments/ptp_pick_resident.py) `def _do_one(self, color, require_fresh=False)` + 메모리 [[verification_must_exercise_call_path]]. owner=Claude, 본 세션 내 closed.

### 무엇을 했는가
`container_pick_gate` 노드(거리 게이트 + 색 시간-다수결) 기능 검증을 위해 임시 `/tmp/fake_placebox.py`(가짜 `/place_box/info`, "green" 다수 발행)를 `setsid python3 ... &` 로 여러 번 띄워 테스트했다. 매번 `pkill -f fake_placebox` 로 정리했다고 **가정**하고 다음 작업으로 넘어갔다. 이후 사용자가 "노란 박스를 못 잡는다"고 하자 place_box 색 분류기(HSV) 버그로 의심해 `color_classifier.cpp` hue 경계(Yellow [30,70)/Green [70,170))까지 한참 분석했다.

### 무엇이 잘못이었나
`pkill` 이 `setsid` 로 분리된 fake_placebox **2개를 못 죽여 계속 살아서** `/place_box/info` 에 가짜 "green" 을 발행하고 있었다. 진짜 place_box 노드는 정확히 "yellow"(h=46)를 내는데, 가짜 green 이 섞여(`/place_box/info` Publisher count=3) 게이트가 **green 을 lock** → 노란 미니박스가 `mini-box-green` 검출에서 제외 → 로봇이 안 움직였다. **"분류기 버그"는 없었고, 내가 만든 테스트 오염이 원인**이었는데, 그걸 모른 채 실로봇 디버깅·코드 분석을 여러 턴 허비하고 사용자를 혼란시켰다.

### 사용자 지적
"노란색 박스인데..", "cloud point색은 노란색이 명확히 보이는데..", "cloud point 색과 비교 해 볼 것" — "명백히 노란색인데 왜 green이냐"를 반복 지적. 그 비교를 하다가 `ros2 topic info /place_box/info` 의 Publisher count=3(진짜 1 + fake 2)을 발견해 비로소 원인 확인.
