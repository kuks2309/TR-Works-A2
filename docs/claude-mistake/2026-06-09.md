# Claude 실수 기록 — 2026-06-09

## 2026-06-09 00:30 (KST) — 라이브 운영 토픽에 테스트 publisher 잔존 오염 → 없는 분류기 버그를 여러 턴 추적

### 무엇을 했는가
`container_pick_gate` 노드(거리 게이트 + 색 시간-다수결) 기능 검증을 위해 임시 `/tmp/fake_placebox.py`(가짜 `/place_box/info`, "green" 다수 발행)를 `setsid python3 ... &` 로 여러 번 띄워 테스트했다. 매번 `pkill -f fake_placebox` 로 정리했다고 **가정**하고 다음 작업으로 넘어갔다. 이후 사용자가 "노란 박스를 못 잡는다"고 하자 place_box 색 분류기(HSV) 버그로 의심해 `color_classifier.cpp` hue 경계(Yellow [30,70)/Green [70,170))까지 한참 분석했다.

### 무엇이 잘못이었나
`pkill` 이 `setsid` 로 분리된 fake_placebox **2개를 못 죽여 계속 살아서** `/place_box/info` 에 가짜 "green" 을 발행하고 있었다. 진짜 place_box 노드는 정확히 "yellow"(h=46)를 내는데, 가짜 green 이 섞여(`/place_box/info` Publisher count=3) 게이트가 **green 을 lock** → 노란 미니박스가 `mini-box-green` 검출에서 제외 → 로봇이 안 움직였다. **"분류기 버그"는 없었고, 내가 만든 테스트 오염이 원인**이었는데, 그걸 모른 채 실로봇 디버깅·코드 분석을 여러 턴 허비하고 사용자를 혼란시켰다.

### 사용자 지적
"노란색 박스인데..", "cloud point색은 노란색이 명확히 보이는데..", "cloud point 색과 비교 해 볼 것" — "명백히 노란색인데 왜 green이냐"를 반복 지적. 그 비교를 하다가 `ros2 topic info /place_box/info` 의 Publisher count=3(진짜 1 + fake 2)을 발견해 비로소 원인 확인.

### 사유 / 가설
- `pkill -f` 의 결과(사멸 여부)를 `pgrep` 로 **검증하지 않고** "정리됨"으로 가정.
- 라이브 운영 토픽에 테스트 데이터를 **직접 발행**한 것 자체가 위험(운영 데이터와 섞임). `setsid` 로 띄워 셸 종료 후에도 잔존.
- 증상(green)을 곧장 **코드 버그로 단정**하고, 토픽 그래프(발행자 수)부터 보지 않음.

### 재발 방지
- **라이브 운영 토픽에 테스트 데이터를 직접 발행하지 않는다.** 부득이하면 별도 토픽/도메인에서.
- 테스트 publisher/노드는 종료 후 **반드시 `pgrep` 로 사멸 확인**(특히 `setsid`/`&` 분리 기동분). 정리 명령의 종료코드/결과를 신뢰하지 말 것.
- 토픽 값이 이상할 때 **먼저 `ros2 topic info <topic>` 로 Publisher count(중복/오염)부터** 보고 코드를 의심한다 — 중복 노드/잔존 발행자는 본 프로젝트 재발 패턴([[ros2_domain_pollution]], 중복 resident 사례).
